# 클라우드 MLOps 웹 교재 작성 가이드

이 문서는 `0060.kr`에서 사용하는 웹 기반 강의 콘텐츠의 작성·개정 기준이다. PPT와 외부 슬라이드 생성 도구를 전제로 하지 않는다.

## 1. 수업과 화면의 기본 조건

- 수업은 15주이며 매주 50분 수업 4회, 총 200분이다.
- 교시 사이에는 10분 휴식이 있다.
- 학생은 Python 기초는 알지만 클라우드·Linux·Docker·MLOps 경험은 없다고 가정한다.
- 학생용, 강사 PT용, 강사 제어용 화면은 같은 장표 번호를 공유한다.
- 학생 입력·선택·완료·질문은 강사 화면에서 실시간 확인할 수 있어야 한다.
- 수업 시간과 진행 지시는 학생용·PT용 장표에 표시하지 않는다. 강사 제어 화면과 발표자 노트에만 둔다.

## 2. 가장 중요한 서사 원칙

### 선행 설명 없는 용어를 사용하지 않는다

각 장표는 학생이 바로 앞 장표까지의 내용만 알고 있어도 이해할 수 있어야 한다.

1. 학생이 이해할 수 있는 구체적인 상황을 먼저 보여 준다.
2. 그 상황에서 필요한 기능이나 문제를 쉬운 말로 설명한다.
3. 설명한 내용에 기술 용어를 붙인다.
4. 해당 용어를 이번 수업에서 어디에 사용할지 연결한다.

예를 들어 첫 수업에서는 `자전거 운영자가 날짜와 날씨를 입력해 예상 대여량을 확인한다`는 상황을 먼저 보여 준다. 이후 데이터, 모델, 서비스, 클라우드, 운영 문제를 차례로 설명한 뒤 MLOps를 정의한다.

### 활동의 전제를 먼저 안내한다

- 팀 운영 원칙이나 역할을 보여 주기 전에 이 과목이 3~4인 팀 프로젝트임을 먼저 안내한다.
- 팀 프로젝트를 하는 이유를 설명한 뒤 팀 구성 절차와 역할을 소개한다.
- 제출 활동 전에 제출 위치·파일·완료 조건을 먼저 안내한다.
- AWS 실습 전에 계정·리전·비용·보안 기준을 먼저 안내한다.

### 같은 도입을 반복하지 않는다

온보딩을 추가한 뒤 기존 과목 소개나 도입 질문이 다시 나오지 않도록 전체 순서를 검토한다. 새 구간을 앞에 덧붙이는 방식보다 중복되는 기존 구간을 교체한다.

## 5. 장표 본문 작성 기준

- 한 장에는 새 개념 하나 또는 학생 행동 하나만 둔다.
- 제목은 주제를 나열하지 말고 그 장표의 결론을 문장으로 쓴다.
- 번역체, 과장된 문구, 근거 없는 통계, 학생 경험을 임의로 가정하는 질문을 쓰지 않는다.
- `이미 해 봤죠`, `왜 아무도 못 쓸까요` 같은 표현을 사용하지 않는다.
- 카드와 구호를 반복해 분량을 채우지 않는다.
- 비교는 표, 순서는 단계도, 실습은 실제 화면을 사용한다.
- 긴 명령어와 전체 절차를 작은 글자로 한 장에 넣지 않는다.
- 활동 장표에는 학생이 지금 해야 할 행동과 완료 조건이 보여야 한다.
- 학생이 입력할 수 있는 장표에는 입력·선택·체크 요소를 실제로 제공한다.

## 6. 발표자 노트 작성 기준

발표자 노트는 본문 요약이나 강사용 업무 지시가 아니라, 강사가 그대로 읽고 수업을 진행할 수 있는 대본이다. `설명한다`, `입력하게 한다`, `답을 확인한다`처럼 강사가 다시 해석해야 하는 문장을 쓰지 않는다. 학생에게 할 말, 응답 뒤에 할 말, 다음 장으로 연결할 말을 완결된 문장으로 적는다.

- `[말하기]`: 강사가 실제로 말할 완결된 문장
- `[학생에게 그대로 말하기]`: 질문, 학생 행동, 입력 위치와 기다릴 시간을 학생에게 직접 안내하는 문장
- `[응답 후 그대로 말하기]`: 응답 분포·완료 수·학생 답을 본 뒤 강사가 실제로 말할 정리 문장
- `[화면을 설명하며 말하기]`: 표·단계도·목록을 어떤 순서로 읽을지 포함한 설명 문장
- `[강조]`: 오해, 오류, 비용, 보안상 주의점을 학생에게 직접 말하는 문장
- `[다음 장으로 연결하며 말하기]`: 다음 장표가 필요한 이유를 학생에게 말하는 문장
- `[출처]`: 외부 자료나 비자명한 주장에 대한 공식 문서 링크

좋지 않은 예:

> 모델과 서비스의 차이를 설명한다.

좋은 예:

> [말하기] 모델이 완성되어도 운영자에게 모델 파일을 보내고 직접 실행하라고 할 수는 없습니다. 입력 화면, 값을 전달하는 연결부, 결과와 오류를 보여 주는 화면이 함께 필요합니다.
>
> [학생에게 그대로 말하기] 화면의 네 항목을 읽고 사용자가 직접 보는 부분을 골라 주세요. 지금부터 1분 드리겠습니다.
>
> [응답 후 그대로 말하기] 입력 화면과 결과 화면은 사용자가 직접 보고, 연결부와 모델은 화면 뒤에서 동작합니다. 서로 다른 답 두 개를 함께 읽어 보겠습니다.
>
> [다음 장으로 연결하며 말하기] 이 구성 전체를 다음 장에서 서비스라고 정의하겠습니다.

## 7. 세 화면의 정보 분리

### 학생용

- 현재 배울 내용과 지금 해야 할 일
- 입력·선택·체크·완료 기능
- 팀 생성, 팀 코드 참여, 팀원 확인과 확정 동의
- 첨부파일과 공식 문서·AWS 콘솔 링크
- Q&A 질문과 본인 질문의 답변

### 강사 PT용

- 학생용과 같은 핵심 장표
- 학생 접속 주소와 수업 코드
- 공개를 선택한 익명 응답과 완료 현황
- 권장 시간, 강사 메모, 학생 이름은 표시하지 않음

### 강사 제어용

- 현재/전체 장표 수, 현재 시각, 권장 시간, 타이머
- 학생·PT 접속 정보
- 출석·참여·답안·완료·질문 현황
- 팀별 인원, 미배정 학생, 팀 이동·병합·해산·확정·잠금과 LMS용 CSV
- 하단 발표자 대본과 첨부파일·공식 링크

### 팀 구성 장표

- 학생에게 팀 이름과 팀원 명단을 일반 입력란에 다시 적게 하지 않는다.
- 팀 구성 활동에는 `teamBuilder: true`를 지정해 실시간 팀 구성 화면을 장표 안에 표시한다.
- 학생은 팀을 만들거나 네 자리 팀 코드로 참여하고, 3~4명 전원이 동의하면 확정된다.
- 팀원이 바뀌면 기존 확정 동의는 초기화된다.
- 강사는 미배정 학생을 배치하고 팀을 합치거나 해산한 뒤 최종 구성을 잠근다.
- 팀 구성이 끝나면 강사 화면에서 LMS 등록용 CSV를 내려받는다.

### 기초 진단 장표

- 이후 주차의 설명 깊이와 실습 속도를 조정하기 위한 진단은 평가용 퀴즈와 구분한다.
- 여러 영역을 한 번에 진단할 때는 한 장표에 여러 객관식 문항을 둘 수 있다.
- 과목 전체의 선행지식을 확인하는 진단은 구체적인 서비스 사용 장면으로 수업 목적을 먼저 보여 준 뒤, 새 기술 용어를 본격적으로 설명하기 전에 배치한다.
- 모든 문항에 `모르겠다`를 넣고, 확실하지 않을 때 추측하지 말고 이를 선택하도록 안내한다.
- 진단 장표에는 개인별 정답 수가 성적에 반영되지 않는다고 명시한다.
- 강사 화면에는 문항별 정답·오답·모름·미응답 수를 집계하고, PT 화면에는 이름을 공개하지 않는다.
- 진단 다음 장표에는 개별 답안을 제외한 선택지별 비율·미응답 비율·정답·해설을 제공하고, 새로고침하거나 재접속해도 같은 익명 집계를 볼 수 있게 한다.
- `모르겠다`나 오답이 많은 문항은 이후 주차의 보충 설명·공통 예제·실습 단계에 반영한다.

## 8. AWS 실습 장표

- 학생이 클릭하거나 상태를 확인하는 단계마다 실제 화면을 사용한다.
- 대표 화면 몇 장만 골라 중간 단계를 생략하지 않는다.
- 화면마다 콘솔 이동 경로, 확인할 값, 실수하기 쉬운 부분, AWS 공식 문서 링크를 제공한다.
- 가짜 콘솔 화면이나 임의의 계정·리소스 식별자를 만들지 않는다.
- 기본 리전은 서울(`ap-northeast-2`)이다.
- 비밀번호, 인증 코드, 액세스 키, 비밀 키, 세션 토큰은 화면·응답·저장소에 남기지 않는다.
- 계정 번호와 리소스 식별자는 공개 범위를 확인한 뒤 사용한다.
- 비용 자원은 생성 전에 이름·예상 비용·종료 시점을 안내하고, 수업 뒤 잔여 자원 확인 절차를 제공한다.

## 9. 첨부파일과 학생 배포

- 실습 전에 받을 파일의 이름과 용도를 장표에서 먼저 설명한다.
- 해당 장표에서 직접 내려받을 수 있어야 한다.
- 다운로드 위치, 압축 해제, 확인 명령, 정상 결과를 제공한다.
- 학생이 수정할 파일, 읽기 전용 파일, 제출할 파일을 구분한다.
- 실패한 학생이 완성본이나 체크포인트로 복구하는 절차를 제공한다.
- 실제로 준비되지 않은 URL·QR 코드·저장소 주소를 만들지 않는다.
