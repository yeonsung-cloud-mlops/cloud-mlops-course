## 3. 2주차 — Linux와 EC2 개발환경

### 이번 주 핵심 메시지

EC2는 어려운 검은 화면이 아니라, 필요할 때 빌려 쓰고 사용 후 끄는 원격 컴퓨터다. 접속 방법·권한·리전·상태를 순서대로 확인하면 대부분의 문제를 찾을 수 있다.

### 슬라이드 서사

1. “컴퓨터가 교실에 없는데 브라우저만으로 프로그램을 실행할 수 있을까?”로 시작한다.
2. 로컬 PC와 EC2의 차이를 위치·접속·과금·종료 관점에서 비교한다.
3. 퍼블릭 IP를 직접 개방하는 방식보다 Session Manager 같은 안전한 접속 경로를 먼저 설명한다.
4. 인스턴스 생성 → 역할 연결 → 접속 → Linux 명령 → Python 가상환경 → S3 접근 순으로 진행한다.
5. 마지막에는 인스턴스 `running`, `stopped`, `terminated` 차이를 화면으로 비교한다.

### 반드시 전달할 개념

- EC2 인스턴스, AMI, 인스턴스 유형, EBS
- Linux 현재 위치·파일·권한·프로세스
- 보안그룹은 서버 앞의 방화벽
- 키 파일보다 역할·Session Manager를 우선하는 이유
- EC2를 중지해도 EBS 요금은 남을 수 있음

### 실습과 제출 증거

- 허용된 인스턴스 유형으로 EC2 생성
- IAM 인스턴스 역할과 태그 확인
- Session Manager 또는 승인된 접속 방식으로 로그인
- Python 가상환경·필수 패키지 설치
- S3 파일 다운로드 및 업로드
- 제출: 인스턴스 상태, 접속 터미널, Python 버전, S3 접근 결과

### 사용할 화면과 링크

- 실제 화면 10장: `개정본/assets/aws-console/week02`
- 우선 화면: 인스턴스 시작 마법사, AMI·유형·키·보안그룹·스토리지, 인스턴스 목록과 상태
- [EC2 시작 마법사](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-launch-instance-wizard.html)
- [Session Manager](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager.html)

## 4. 3주차 — 데이터 파이프라인과 문제 정의

### 이번 주 핵심 메시지

모델보다 먼저 정해야 할 것은 “어떤 입력으로 무엇을 예측하며, 성공을 무엇으로 판단할 것인가”이다. 원본 데이터는 보존하고 가공 과정은 코드로 다시 실행할 수 있어야 한다.

### 슬라이드 서사

1. 같은 CSV가 `final.csv`, `final2.csv`, `진짜최종.csv`로 늘어나는 상황으로 시작한다.
2. 원본을 덮어쓰면 왜 실험을 다시 할 수 없는지 보여준다.
3. `raw → processed → features` 흐름을 한 장의 데이터 이동도로 설명한다.
4. 일상 문장을 입력·목표값·사용 시점·평가지표가 있는 ML 문제로 바꾼다.
5. 데이터 카드와 문제정의서를 팀 프로젝트의 첫 공식 문서로 연결한다.

### 반드시 전달할 개념

- 원본 불변, 데이터 계보, 재현 가능한 전처리
- 분류·회귀와 목표 변수
- 학습 시점에 알 수 없는 정보는 입력에 넣지 않음
- 데이터 카드: 출처·컬럼·결측·라이선스·처리 이력
- 좋은 문제 정의: 사용자, 판단, 예측 시점, 지표, 성공 기준

### 실습과 제출 증거

- S3 `raw/`에서 원본을 읽어 전처리 스크립트 실행
- 결과를 `processed/`에 다른 파일로 저장
- 행 수·결측치·스키마 검사
- 팀 데이터 선택, 데이터 카드와 문제정의서 초안 작성
- 제출: 전처리 코드, S3 경로, 데이터 카드, 문제정의서

### 사용할 화면과 링크

- 실제 화면 10장: `개정본/assets/aws-console/week03`
- 우선 화면: S3 버킷·접근 지점·퍼블릭 액세스 차단·원본/가공 경로
- [S3 폴더 사용](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-folders.html)

## 5. 4주차 — 베이스라인 모델 만들기

### 이번 주 핵심 메시지

첫 모델의 목적은 최고 점수를 얻는 것이 아니라 이후 개선을 비교할 기준을 만드는 것이다. 성능이 지나치게 좋다면 데이터 누수부터 의심한다.

### 슬라이드 서사

1. “정답을 입력값에 몰래 넣으면 정확도 100%가 좋은 모델일까?”로 시작한다.
2. 학습·검증·테스트 데이터의 역할을 시험 문제 비유로 설명한다.
3. 문제 유형에 따라 지표가 달라지는 이유를 실제 사례로 비교한다.
4. 전처리와 모델을 `Pipeline` 하나로 묶어야 학습과 예측이 같아진다는 점을 보여준다.
5. 베이스라인 결과표를 M1 문제정의서의 성공 기준과 연결한다.

### 반드시 전달할 개념

- train/validation/test 분리
- 데이터 누수와 학습-평가 시점의 차이
- 정확도, 정밀도, 재현율, F1, MAE·RMSE의 선택 기준
- 단순 모델을 기준선으로 두는 이유
- 모델 파일만이 아니라 전처리 Pipeline을 함께 저장

### 실습과 제출 증거

- 공통 데이터로 베이스라인 Pipeline 학습
- 성능표와 혼동행렬 또는 오차표 작성

## 9. 8주차 — EC2 배포와 데모 화면·중간 시연

## 13. 12주차 — GitHub Actions 배포 자동화

5. GitHub OIDC 토큰 → AWS IAM 역할 → 임시 자격 증명 흐름을 설명한다.
6. 릴리스 태그 `1.1 → 1.2` 배포와 실패 시 직전 태그 롤백을 실행한다.

### 반드시 전달할 개념

- CI와 CD
- GitHub Actions workflow/job/step
- GitHub OIDC와 IAM 신뢰 정책
- ECR 불변 릴리스 태그
- smoke test와 rollback
- 장기 액세스 키를 저장하지 않는 이유

### 실습과 제출 증거

- 브랜치·커밋·PR 경험
- 제공된 Workflow 빈칸 완성
- 테스트·빌드·ECR push·SSM 배포
- 새 버전 health 확인
- 직전 정상 이미지로 롤백

## 14. 13주차 — CloudWatch 모니터링과 운영

### 이번 주 핵심 메시지

서비스가 켜져 있다는 것과 정상이라는 것은 다르다. 로그는 사건, 메트릭은 변화, 알람은 행동해야 할 순간을 알려준다.

### 슬라이드 서사

1. 사용자가 먼저 장애를 알려주는 상황과 운영자가 먼저 알람을 받는 상황을 비교한다.
2. 로그·메트릭·알람을 각각 사건 기록·숫자 추세·조건 통보로 구분한다.
3. 응답 시간 130ms → 920ms → 105ms 변화를 실제 화면으로 보여준다.
4. 정상 → ALARM → 정상 상태 변화를 임계값과 평가 기간으로 설명한다.
5. 모델 서비스에는 시스템 지표뿐 아니라 입력 분포와 예측 분포도 필요함을 소개한다.
6. 팀별 운영 체크리스트, 장애 접수, 1차 조치, 재학습 정책을 작성한다.

### 반드시 전달할 개념

- CloudWatch Logs, Metric, Dashboard, Alarm
- namespace, dimension, period, threshold
- 지연시간·오류율·요청 수
- 데이터 드리프트와 간이 입력 분포 모니터링
- 알람 이후 담당자·확인·조치·기록
- SNS 이메일은 실제 주소가 준비된 경우에만 선택적으로 구성

### 실습과 제출 증거

- 로그 그룹과 로그 스트림 확인
- 사용자 지정 메트릭 전송
- 대시보드 위젯 구성
- HighLatency 알람의 OK → ALARM → OK 확인
- 팀 운영 체크리스트와 M3 완성
- 제출: 로그·그래프·알람 변화·운영표

## 15. 14주차 — 프로젝트 집중 워크숍

### 이번 주 핵심 메시지

3. 팀 A와 팀 B가 README만 교환해 재현하는 절차를 보여준다.
4. 재현 실패는 감점용이 아니라 문서를 고칠 증거로 사용한다.
5. 실제 시연이 실패할 경우를 대비해 60~90초 시연 영상을 만든다.
6. AWS Resource Explorer·EC2·ECR·SageMaker·CloudWatch·Cost Explorer를 순회하며 잔여 자원을 감사한다.

### 반드시 전달할 개념

- 재현성의 사용자 관점
- README의 사전 조건·실행 명령·환경 변수·정상 결과·정리 방법
- 발표에서 모델 구조보다 문제와 결과를 먼저 말함
- 시연 영상은 백업이며 편집 홍보 영상이 아님
- 리소스 감사와 비용 증거

### 실습과 제출 증거

- 다른 팀의 README로 처음부터 실행
- 막힌 단계·원인·수정 내용 기록
- 발표자료와 5분 발표 리허설
- 60~90초 시연 영상
- 전체 AWS 리소스·비용 점검
- 제출: 교차 재현표, 수정 README, 발표 후보본, 영상, 리소스 감사표

## 16. 15주차 — 최종 발표와 리소스 정리

### 이번 주 핵심 메시지

최종 발표는 사용 기술 목록을 읽는 시간이 아니라 문제·근거·작동 결과·운영 경험을 증명하는 시간이다. 학기 종료는 발표가 아니라 백업과 AWS 리소스 정리까지 완료해야 끝난다.

4. 발표 후 삭제 전에 코드·설정·지표·화면·비용 증거를 백업한다.
5. 비싼 리소스부터 SageMaker → EC2/EBS/EIP → ECR → S3 → CloudWatch → IAM·네트워크 순으로 점검한다.
6. Cost Explorer의 데이터 반영 지연을 설명하고 당일 0원 표시만으로 단정하지 않는다.
7. 마지막에는 개인 포트폴리오 README와 다음 학습 경로로 연결한다.

### 반드시 전달할 개념

- 결과를 근거로 말하는 발표
- 데모 실패 대응과 백업 영상
- 백업 후 삭제 원칙
- 중지와 삭제의 차이
- 비용 데이터 반영 지연
- GitHub README에 개인 기여·구성도·실행법·결과·배운 점 기록

### 실습과 제출 증거
